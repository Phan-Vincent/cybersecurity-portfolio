# Detection Engineering Lab

A detection-as-code lab: 15 Sigma rules (13 alerting), a small Sigma evaluator, and
synthetic attack scenarios that prove each rule fires on the attack and stays quiet on
look-alike normal activity. It covers Linux, Windows and the healthcare-specific signals
a SIEM rarely ships with: EHR audit logs and PHI leaving through cloud uploads.

## One-Line Pitch

> "I write detections the way engineers write code: in a standard format (Sigma), mapped to
> ATT&CK, with tests that prove every rule catches its attack and doesn't fire on the
> admin work that looks like it."

## What This Demonstrates

- **Sigma rule writing:** detection maps, modifiers (`contains`, `endswith`, `re`, `cidr`,
  `all`, numeric comparisons), boolean conditions, and Sigma 2.0 **correlation rules**
  (`event_count` for SSH brute force, `value_count` for bulk chart access).
- **False-positive engineering:** a benign baseline of deliberate near-misses (7 failed
  logins against a threshold of 8, `crontab -l`, `vssadmin list shadows`,
  `-ExecutionPolicy`, ProcDump on a non-LSASS process, a clinician's busy shift, a justified
  break-the-glass, PHI sent to *sanctioned* storage). Any alert on it fails the build.
- **Healthcare detections:** EHR record snooping (bulk access, VIP charts outside the care
  team, break-the-glass without a reason) and PHI exfiltration to personal cloud storage.
  These map to the HIPAA Security Rule's audit-control requirement, 164.312(b).
- **ATT&CK mapping:** every alerting rule carries tactic and technique tags, and
  [docs/coverage.md](docs/coverage.md) is generated from the rules and test results.
- **Detection CI:** schema checks, evaluator unit tests, exact threshold boundaries, and a
  check that removing an attack step removes its alert, which rules out rules that pass
  vacuously.

## Rules

| Area | Rules | ATT&CK |
|---|---|---|
| Linux (sshd) | SSH brute force (correlation), root login | T1110.001, T1078.003 |
| Linux (process) | Reverse shell, sudo grant / sudoers write, cron persistence, history wiping | T1059.004, T1548.003, T1053.003, T1070.003 |
| Windows (process) | Encoded PowerShell, LSASS dump, shadow-copy deletion / recovery disabled | T1059.001, T1003.001, T1490 |
| EHR audit | Bulk chart access (correlation), VIP chart without care relationship, break-the-glass without reason | T1213, T1078 |
| Web proxy | PHI (SSN/MRN/DOB DLP match) uploaded to personal cloud storage | T1567.002 |

Two more rules (`ssh_auth_failure`, `ehr_record_view`) are informational building blocks
that feed the correlations and don't alert on their own, per the Sigma correlation spec.

## Scenarios

| Scenario | Story | Expected detections |
|---|---|---|
| `ssh_bruteforce_root` | Internet scanner guesses SSH passwords, then logs in as root | 2 |
| `linux_post_exploitation` | Apache web shell → reverse shell → sudo user → cron jobs → history wiped | 4 |
| `ransomware_precursors` | Pharmacy workstation: encoded PowerShell stager, LSASS dump, shadow copies deleted | 3 |
| `ehr_insider_snooping` | Nurse opens 55 unrelated charts in 45 minutes, a VIP chart, and an unexplained override | 3 |
| `phi_exfiltration` | Billing user uploads a file with SSNs and MRNs to personal cloud storage | 1 |
| `benign_baseline` | Normal admin, clinical and browsing activity built to resemble the attacks | **0** |

All data is synthetic and generated by [`data/generate.py`](data/generate.py): fictional
hosts, users and patients, and IPs from the RFC 5737 documentation ranges.

## How to Run

```bash
pip install -r requirements.txt

python src/run_lab.py                 # run every rule on every scenario; exit 1 on a miss or false positive
python src/run_lab.py --write-docs    # also regenerate docs/coverage.md
python data/generate.py               # regenerate the scenario datasets
pytest -q                             # 95 tests
```

Example output:

```
[PASS] ssh_bruteforce_root.jsonl: 2 alert(s) from 2 rule(s)
       high     ssh_root_login_success <- ssh_bruteforce_root-013
       high     ssh_bruteforce {'source_ip': '203.0.113.45'} <- ssh_bruteforce_root-001, ...
...
[PASS] benign_baseline.jsonl: 0 alert(s) from 0 rule(s)
```

## SIEM Export (official Sigma toolchain)

The rules are also validated and converted with the official
[sigma-cli](https://github.com/SigmaHQ/sigma-cli) / pySigma toolchain, so they are proven
outside this lab's own evaluator. CI runs `sigma check` (schema, conditions and ATT&CK
tags) and regenerates the exports below, failing if the committed copies are stale:

- [`queries/splunk/savedsearches.conf`](queries/splunk/savedsearches.conf): one Splunk
  saved search per alerting rule; correlations become `bin`/`stats` searches.
- [`queries/esql/`](queries/esql/): one Elastic ES|QL query per rule.

```bash
pip install -r requirements-sigma.txt
sigma check rules/
python src/export_queries.py          # add --check to verify instead of write
```

Converting to ES|QL caught a portability bug: two rules first used regular expressions
with `\s` and `(?i)`, which ES|QL's Lucene-based `rlike` doesn't support and which it
matches against the whole value. Both were rewritten with `contains`/`endswith`
modifiers that convert cleanly to every backend, and the scenarios showed identical
detections before and after. No field-mapping pipeline is applied, so the queries use
the rules' own field names. Also, ES|QL's `like` is case-sensitive, whereas Sigma
matching isn't. A deployment would add its SIEM's field mapping and case handling as a
pySigma pipeline.

## Project Structure

```

├── rules/                  # Sigma rules: linux/, windows/, ehr/, proxy/
├── src/
│   ├── sigma_lite.py       # Sigma evaluator (detections, conditions, correlations)
│   └── run_lab.py          # runs scenarios, checks expectations, writes coverage doc
├── data/
│   ├── generate.py         # deterministic synthetic data generator
│   ├── scenarios.yml       # scenario → expected detections
│   └── scenarios/*.jsonl   # generated events
├── docs/coverage.md        # generated ATT&CK coverage and results
├── queries/                # Splunk and ES|QL exports from sigma-cli
└── tests/                  # rule schema, evaluator, end-to-end scenario tests
```

## Limits

`sigma_lite` implements the subset of Sigma these rules need. It raises an error on
anything else, such as keyword searches, `base64` modifiers or `temporal` correlations,
instead of silently ignoring it. The rules use standard Sigma syntax and field names (with
the EHR and proxy fields defined here), so they can be converted for a real SIEM with
[pySigma](https://github.com/SigmaHQ/pySigma) once a backend and field mapping are chosen.
